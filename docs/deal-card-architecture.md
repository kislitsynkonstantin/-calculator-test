# Карточка сделки: архитектура

Черновик на согласование. Написан 08.09.2026 по разговору: «хочу сделать карточку
по аналогии с Битрикс, настроить в первую очередь автоматизацию, автозадачи и
платежи; надо сначала всё проработать».

Ничего из этого пока не сделано. Документ описывает, **что строим, из чего и в
каком порядке**, и называет решения, которые нужно принять до первой таблицы.

---

## 1. Что строим и чего не строим

**Строим:** карточку сделки — объект, вокруг которого собираются расчёты, деньги,
задачи и переписка о ходе работ; движок автоматизации; автозадачи; платежи с планом
и фактом.

**Не строим** (по крайней мере сейчас): лиды и квалификацию, звонки и почту внутри
системы, чаты, склад, зарплаты. Коммерческое предложение у нас уже есть — это
спецификация, и второй сущностью оно не становится.

Граница простая: **в карточке живёт то, у чего есть срок или сумма.** Разговоры и
файлы — прицепом, а не основанием.

---

## 2. Что вскрылось в разведке — и почему это главное

### У платежей нет дат

Платёжный план сегодня считает проценты и суммы, но срок этапа записан **словами**:
«аванс по договору», «при заезде бригады», «по завершении кровельных работ». В коде
это поле `sub` — подпись, а не дата (`PP_DEFAULT_PAYMENTS`, `index.html`).

Отсюда следует то, что определяет всю остальную архитектуру:

> **«Просрочено» невозможно посчитать, пока система не знает, что бригада заехала.**

Значит автоматизация платежей упирается не в экран платежей, а в то, что у сделки
должны быть **производственные стадии**, и наступление стадии должно записываться
с датой. Дата платежа рождается из события, а не из календаря:

```
due_at = <когда наступила стадия «заезд бригады»> + <сколько дней на оплату>
```

До наступления стадии этап «ждёт», а не «просрочен». Это же делает честными
счётчики в боковой панели: «2 просрочены» — про деньги, у которых уже настал срок.

### План живёт внутри снимка расчёта

`contractsConfig` и `ppState` лежат JSON-ом в разделе `payment_plan` пресета.
Запросить их нельзя: чтобы показать «что просрочено по всем объектам», пришлось бы
прочитать каждый пресет и разобрать снимок. **Этапы обязаны стать строками.**

### Автоматика не может жить в браузере

Правило «платёж просрочен на три дня» обязано сработать, когда менеджер спит и
вкладка закрыта. Значит движок — **Edge Function по расписанию** на стороне
Supabase, а не код в `index.html`. Браузер только показывает результат и дёргает
функцию на явных действиях (сменил стадию — пересчитай).

### Что уже есть и переиспользуется

| Есть сейчас | Роль в карточке |
|---|---|
| `presets` (расчёт в JSON) | расчёт сделки; добавляется `deal_id` |
| Платёжный план (проценты, договоры) | считает суммы этапов; этапы переезжают в строки |
| `events` (журнал действий) | лента карточки; добавляется `deal_id` |
| `preset_links` (ссылка клиенту) | документ сделки + факт прочтения (задача 5) |
| `profiles.role` (admin/editor/manager/specialist) | доступ и назначение задач |

Таблица говорит вот что: половина карточки уже написана и лежит в калькуляторе —
расчёт, суммы этапов, журнал событий и ссылка клиенту. Нового кода требуют сама
сделка, строки платежей с фактом, задачи и движок правил; остальное подключается
к существующему, а не пишется заново.

## 3. Сущности и связи

```
        ┌──────────────┐
        │    Сделка    │  клиент, объект, менеджер, стадия, сумма
        └──────┬───────┘
   ┌───────────┼────────────┬──────────────┬───────────────┐
   │           │            │              │               │
┌──▼───┐  ┌────▼─────┐  ┌───▼────┐   ┌─────▼────┐   ┌──────▼──────┐
│Расчёт│  │  Этап    │  │ Задача │   │ Событие  │   │  Документ   │
│пресет│  │ платежа  │  │        │   │  ленты   │   │ ссылка,файл │
└──────┘  └────┬─────┘  └────────┘   └──────────┘   └─────────────┘
               │
         ┌─────▼─────┐
         │   Факт    │  сколько пришло и когда
         │  оплаты   │
         └───────────┘
```

**Сделка** — одна на объект, а не на расчёт. У клиента может быть три варианта бани:
это три пресета внутри одной сделки, и платежи с задачами висят на сделке, а не
разъезжаются по вариантам.

**Факт оплаты — отдельная строка, а не поле в этапе.** Доплаты частями обычны, и
«оплачено 300 000 из 640 000, остаток ждём» должно читаться из данных, а не
восстанавливаться по памяти.

### Таблицы

```sql
deals            id, number, title, client_name, client_phone, client_email,
                 address, manager_id, stage, status(active|won|lost), lost_reason,
                 amount, main_preset_id, created_at, updated_at, closed_at

presets          + deal_id            -- одна колонка вместо новой таблицы связи

deal_stages      key, name, ord, kind(sale|prod), is_final   -- справочник
deal_stage_log   deal_id, stage, entered_at, by_user         -- когда наступила

payments         id, deal_id, contract_code, slot, label,
                 plan_amount, plan_stage, due_days, due_at,
                 status(ждёт|срок настал|оплачен|частично|снят), created_at
payment_facts    id, payment_id, amount, paid_at, method(нал|безнал), note, by_user

tasks            id, deal_id, title, body, assignee_id, due_at,
                 status(открыта|сделана|снята), source(руками|правило:<ключ>),
                 dedup_key, created_by, created_at, done_at

events           + deal_id            -- лента карточки в том же журнале
```

`due_at` у платежа пустой, пока не наступила `plan_stage`; движок проставляет его
в момент наступления и с этого мгновения умеет считать просрочку.

## 4. Стадии

Предложение — **одна лента**, а не две воронки:

```
Новая → Расчёт → Проверка → У клиента → Договор →
Фундамент → Каркас → Кровля → Утепление → Отделка → Парная и печь → Сдача
                                                              → Выиграна / Проиграна
```

Почему одна: деньги привязаны к производственным событиям, и разрыв ленты надвое
означает две карточки на один объект — вторую никто не ведёт. В Битриксе это две
воронки именно потому, что там продажа и производство — разные отделы; у нас
менеджер тянет объект целиком.

Стадия меняется руками. Автоматика стадию **предлагает**, но не двигает сама —
кроме случаев, где событие однозначно (подписан договор, пришёл финальный платёж).

## 5. Движок автоматизации

Правило — три части, как везде: **когда · при каких условиях · что сделать**.

| Часть | Из чего берётся |
|---|---|
| Когда (триггер) | стадия наступила · платёж без движения N дней · расчёт согласован · клиент открыл ссылку · задача просрочена · сделка стоит N дней |
| При каких условиях | стадия сделки · сумма больше X · роль автора · есть ли непройденная проверка |
| Что сделать | завести задачу · проставить срок платежу · написать в ленту · предложить стадию · уведомить |

Таблица говорит вот что: триггеры делятся на два вида — событийные (что-то
произошло прямо сейчас) и временны́е (что-то не произошло за N дней), и именно
вторые требуют серверного расписания. Условия отбирают, к каким сделкам правило
применимо, а действия почти все сводятся к одному — завести задачу; остальное
(срок, лента, стадия) идёт довеском.

### Где выполняется

- **Edge Function `automation`** в Supabase. Два входа: по расписанию (раз в час —
  временны́е правила) и по вызову из браузера (явное действие: сменил стадию,
  внёс оплату).
- Браузер правила **не выполняет** и не хранит: иначе всё, что происходит ночью,
  не происходит вовсе.

### Зашитые правила или редактор правил

Начинаем с **зашитых в функцию** — но описанных тем же строением (триггер,
условия, действия), чтобы редактор потом лёг сверху без переписывания. Редактор
правил — отдельный продукт со своим интерфейсом, отладкой и «почему это правило
не сработало»; заводить его раньше, чем набор правил устоится, значит строить
конструктор для трёх деталей.

Ориентир для перехода к таблице `automation_rules`: **правил стало больше
пятнадцати или Константин трижды попросил поменять условие.**

### Первые правила (черновик)

1. Наступила стадия «Заезд бригады» → у этапа «При заезде бригады» проставляется
   срок (+3 дня) и статус «срок настал».
2. Срок платежа настал и факта нет 3 дня → задача менеджеру «Забрать оплату».
3. Расчёт отправлен клиенту, ссылку открыли, ответа нет 2 дня → задача «Позвонить».
4. Сделка на стадии «У клиента» стоит 7 дней → задача «Сделка стоит неделю».
5. Стадия «Договор» без подписанного договора 3 дня → задача «Подписать договор».
6. Пришёл финальный платёж по всем договорам → предложить стадию «Сдача».
7. Спецификация не проверена, а сделка уже на «У клиента» → задача «Проверить
   спецификацию» (связка с задачей 4 очереди).

## 6. Автозадачи: правила, чтобы они не превратились в спам

- **Ключ повтора.** У задачи от правила есть `dedup_key = правило:сделка:объект`.
  Пока по этому ключу открыта задача, вторая не заводится. Без этого правило
  «платёж просрочен» за неделю нарожает семь одинаковых задач.
- **Задача закрывается сама**, когда условие ушло: пришла оплата — задача «Забрать
  оплату» снимается, в ленту пишется «снята автоматически». Иначе менеджер
  закрывает руками то, что уже неверно, и перестаёт верить списку.
- **Срок обязателен.** Задача без срока не задача, а запись. Правило всегда ставит
  срок, даже если это «сегодня».
- **Исполнитель — менеджер сделки**, если правило не сказало иначе. Задача без
  исполнителя не делается никем.
- **Задача от правила видна как таковая.** В карточке видно, кто её создал —
  человек или правило, и какое именно: иначе «откуда это взялось» становится
  вопросом ко мне, а не к системе.

## 7. Платежи

**Строки вместо снимка.** При переводе сделки на стадию «Договор» план из расчёта
разворачивается в строки `payments`: договор, номер этапа, подпись, сумма, стадия-
триггер, срок в днях. Дальше строки живут своей жизнью — расчёт может меняться,
план уже согласован.

**Пересчёт после подписания — вручную и с предупреждением.** Если расчёт изменился
после разворачивания плана, показываем расхождение и кнопку «пересобрать план», а
не пересобираем молча: под планом уже стоит подпись клиента.

**Статусы:** ждёт (стадия не наступила) · срок настал · частично · оплачен · снят.
«Просрочен» — не статус, а свойство: срок настал, факта нет, прошло больше N дней.
Иначе пришлось бы держать статус в актуальном состоянии кроном по всем строкам.

**Сводка «Оплаты» по всем сделкам** — это просто выборка по строкам, и она
становится возможной ровно в тот момент, когда строки появились.

## 8. Доступ

Решение нужно до первой таблицы, потому что оно формирует RLS.

Предложение:

| Роль | Сделки | Платежи | Задачи |
|---|---|---|---|
| manager | только свои | по своим сделкам | свои |
| specialist | только свои | по своим сделкам | свои |
| editor | все | все | все |
| admin | все | все, включая удаление | все |

Таблица говорит вот что: менеджер и специалист живут в своём кусочке — видят
сделки, где они назначены, и деньги с задачами по ним; редактор и администратор
видят всё, а право удалять платёж есть только у администратора, потому что
удалённый платёж — это пропавшие деньги в отчёте. Ровно это и ложится в правила
доступа Supabase, по одной политике на таблицу.

Отдельно: **чужую задачу видно, но не закрыто.** Иначе «сделал» ставит не тот, кто
делал.

## 9. Карточка на экране

Устройство — из утверждённого макета боковой панели: слева колонка сервисов,
справа лист. Карточка сделки — это лист.

```
┌ Сделка № 1043 · Фахверковая баня «Бонн» 4×4 ──────── 1 796 835 ₽ ┐
│ Иванов И. И. · +7 900 … · Дмитров, СНТ «Луч» · менеджер К. Кислицын │
├──────────────────────────────────────────────────────────────────┤
│ Новая · Расчёт · Проверка · ▍У клиента · Договор · Фундамент · … │  ← лента стадий
├──────────────────────────────────────────────────────────────────┤
│ Обзор · Расчёты · Платежи · Задачи · Документы · Лента            │  ← вкладки
├───────────────────────────────────┬──────────────────────────────┤
│ содержимое вкладки                │ Ближайшая задача             │
│                                   │ Ближайший платёж             │
│                                   │ Ссылка клиенту · открыта 2×  │
└───────────────────────────────────┴──────────────────────────────┘
```

- **Обзор** — что происходит: срок ближайшего платежа, открытые задачи, последние
  события. Не форма с полями: поля прячутся в «Реквизиты».
- **Расчёты** — пресеты сделки, один помечен основным; открывается калькулятором.
- **Платежи** — строки плана с фактом, кнопка «Внести оплату».
- **Задачи** — свои и от правил, с пометкой источника.
- **Лента** — события из `events`, включая «правило завело задачу» и «клиент открыл
  ссылку».

Правило оформления то же, что везде: язык «Бланка», коробок нет, разделяют линейки.

## 10. Порядок работ

Каждый шаг заканчивается выкладкой на тест и работает сам по себе.

1. **Сделка и связь с расчётом.** Таблица `deals`, `presets.deal_id`, страница
   списка и карточка с вкладками «Обзор» и «Расчёты». Автоматики нет — есть хребет,
   на который всё вешается. Сделка заводится из открытого расчёта одним нажатием;
   старые пресеты остаются без сделки и работают как работали.
2. **Стадии.** Справочник, лента в карточке, запись наступления с датой в
   `deal_stage_log`, событие в ленту. Без этого шага автоматика невозможна —
   ей не от чего считать сроки.
3. **Платежи строками.** Разворачивание плана из расчёта в `payments`, вкладка
   «Платежи», внесение факта руками, сводка «Оплаты» по всем сделкам.
4. **Движок и автозадачи.** Edge Function, расписание, 5–7 правил из раздела 5,
   ключ повтора, автозакрытие, пометка источника. Вкладка «Задачи» и сервис
   «Задачи» со сводкой.
5. **Уведомления.** Почта или телеграм по задачам со сроком «сегодня». Отдельно,
   потому что упирается в канал доставки, а не в карточку.
6. **Редактор правил.** Когда набор устоится — таблица `automation_rules` и экран
   для неё.

Шаги 1–2 не дают менеджеру ничего нового на глаз и потому кажутся необязательными.
Они и есть работа: без даты наступления стадии всё остальное неисполнимо.

## 11. Открытые вопросы

С моими предложениями — нужно подтвердить или поменять.

1. **Стадии.** Список из раздела 4 — рабочий или у вас другая последовательность?
   Особенно после договора: где на самом деле проходят границы этапов.
2. **Сроки оплаты.** Сколько дней даётся на платёж после наступления стадии —
   одинаково для всех этапов или по-разному? Предлагаю 3 дня по умолчанию, с
   правкой у конкретного этапа.
3. **Факт оплаты.** Вносится руками менеджером или подтягивается откуда-то (банк,
   1С, таблица)? Предлагаю руками, с полем «нал / безнал», и подумать про импорт
   выписки позже.
4. **Кто видит чужое.** Таблица в разделе 8 — так или иначе? Это самое дорогое
   решение для переделки.
5. **Одна лента стадий или две воронки.** Предлагаю одну, обоснование в разделе 4.
6. **Что делать со старыми пресетами.** Предлагаю не мигрировать: сделка заводится
   из расчёта по кнопке, старое остаётся как есть.
7. **Номер сделки.** Сквозной счётчик или от номера договора? Предлагаю свой
   сквозной, а номер договора — отдельным полем.
8. **Проигранные сделки.** Нужна ли причина отказа списком (дорого, выбрал другого,
   передумал, не отвечает)? Предлагаю нужна: без неё аналитика по отказам
   невозможна, а это единственное, что показывает, где теряем.

## 12. Чего я бы не делал

- **Не заводить редактор правил первым.** Конструктор для трёх правил — это работа
  без пользы; правила сначала должны пожить зашитыми.
- **Не привязывать деньги к календарным датам.** «Оплата до 12.09» ломается о
  первую же сдвинутую бригаду; срок должен считаться от события.
- **Не двигать стадии автоматикой без спроса.** Стадия — это то, за что отвечает
  человек; система предлагает, человек подтверждает.
- **Не делать задачи перепиской.** Комментарий в задаче — да; обсуждение — в
  мессенджере.
